# 낚시월드 작업 지침

Godot 4.4.1 안드로이드 세로형 도트 낚시게임. 한국어로 간결히 답하고 승인된 작업은 직접 수행한다. 최신 사용자 지시가 우선한다.

## 시작과 원본
- 저장소: https://github.com/znzkznzk96-rgb/nakshiworld-update
- 새 작업은 START_HERE → docs/CONTINUE_HERE 경로를 따른다. AGENTS, 이 지침, WORK_STATE, GAME_BIBLE, 활성 브랜치 HANDOFF, 최신 CHANGELOG 항목과 실제 Release/관련 Actions/배포 workflow를 확인한다. 활성 브랜치 포인터가 바뀌었으면 해당 브랜치의 최신 지침도 따른다.
- 같은 세션에서 이미 읽은 파일은 원격 SHA/관련 diff가 바뀌었을 때 변경 부분만 재확인한다. 과거 이력 전체나 모든 브랜치를 반복해서 읽지 않는다. 충돌/누락/관련 작업이 있을 때만 추가 조사한다.
- 게임 수정은 최신 Release game-source.zip + 활성 브랜치 overlay + 삭제 명세로 복원한다. 저장소 game/만 전체 프로젝트로 가정하지 않는다. 검증한 소스·도구·import 캐시는 기준 버전과 변경 diff를 확인해 재사용한다. 문서만 수정할 때는 게임 복원/빌드하지 않는다.

## 기록과 즉시 저장
- GAME_BIBLE: 확정·미정·폐기된 기획/세계관/사용자 결정의 원본. 날짜·근거·대체 관계를 남긴다. 구현을 승인 근거로 해석하지 않는다.
- WORK_STATE: 활성 브랜치, 현재 작업, 실제 배포 상태와 다음 작업의 짧은 포인터.
- HANDOFF: 현재 목표·완료·남은 일·실패/검증 근거 링크·다음 행동. 최신 본문을 교체하며 과거 작업은 docs/historical에 보존한다. CHANGELOG는 변경 묶음별 결과만 적는다. START_HERE/CONTINUE_HERE는 안정적인 진입 절차이며 매 단계 상태를 복사하지 않는다.
- 사용자가 게임 결정을 확정/변경하면 코드 수정이 없어도 즉시 GAME_BIBLE에 기록한다. 같은 메시지의 결정은 묶어도 된다. 그 결정에 의존하는 구현 전 GAME_BIBLE·관련 변경물·HANDOFF·WORK_STATE를 work/*에 원격 저장하고 SHA와 변경 파일 내용을 확인한다. 단순 진행은 의미 있는 변경 묶음마다 저장한다. 채팅 종료 때까지 미루지 않는다.
- 이미 검증된 원격 저장 경로를 먼저 사용한다. 이 환경에서 Git CLI push 인증 실패가 확인되었으므로 연결된 GitHub API를 우선하고 실패한 push를 반복하지 않는다. 다른 환경에서는 사용 가능한 경로를 확인한다. 원격 head/expected SHA를 확인해 타인 변경을 덮지 않는다.
- 원격 저장 모두 실패 시 로컬에만 남은 구체 결과를 즉시 알린다. 저장되지 않은 작업이나 전체 채팅이 자동 복구된다고 약속하지 않는다. 기록/에셋을 저장소에서 먼저 찾고 불필요한 재첨부/재질문을 하지 않는다.
- 문서를 줄일 때 원본을 그대로 이력에 보존하고 링크한다. 결정 근거·실패·검증 기록을 삭제하지 않는다. 상세 해시·로그는 검증 문서 한 곳에 두고 다른 문서는 링크한다.

## 효율적인 실행과 검증
- 원격 상태 확인 → 필요한 수정 → 관련 검사 → 결과 표시 → 의미 있는 원격 checkpoint. 새 결정은 위 즉시 저장 절차를 먼저 수행한다. 화면 결과는 준비되는 즉시 직접 보여주고 검증/저장/배포 상태를 표시한다. 진행 중에는 60초 이상 설명 없이 기다리게 하지 않는다.
- 개발 중은 변경의 영향 범위에 맞는 검사만 실행한다. 세이브·공통 시스템 변경 및 배포 직전에는 필수 전체 검사를 수행한다. 기존 검증은 소스/설정/도구가 동일하고 새 실패가 없을 때 재사용한다. 변경·실패·미해결 의심 없이 동일 검사를 반복하지 않는다. 문서만 변경하면 링크·JSON·기록 보존·diff 및 배포 트리거만 검사한다.
- 독립된 읽기/검사는 가능한 범위에서 묶거나 병렬 실행한다. 공유 세이브·임시경로를 분리하고 의존 작업/원격 ref 갱신은 순서대로 한다. 유료 이미지 생성은 병렬화 대상이 아니다.

## 배포와 보호
- 중간 저장은 work/*에서 한다. 실제 workflow 조건을 확인해 승인 없는 자동 배포를 막는다. 문서 변경 때문에 게임 버전/PCK를 다시 만들지 않는다. 작업 승인과 과거 배포 승인을 새 게임 패치의 포괄 승인으로 해석하지 않는다.
- 배포 요청 시 검증한 소스를 게시하고 버전·소스 커밋·전체소스ZIP·PCK·version.json 실제 존재/크기/SHA256 및 운영 다운로드를 확인한다. 결과와 다음 작업을 다시 원격 기록한다. 수정/검증/공개/휴대폰 적용 성공은 구분한다.
- 승인 UI·아트·밸런스를 임의 변경하지 않는다. 미정 수치는 준비 중으로 둔다. 기존 세이브 보호, 격리 테스트, 앱 삭제/데이터 초기화 기본 해결 금지. 비밀번호·토큰·서명키·실제 사용자 세이브 공개 금지. historical 소스를 최신 위에 덮지 않는다.

## 물고기와 유료 아트 — 필수 유지
- 제작 전 docs/FISH_ART_RULES.md 전체를 읽는다. 전 낚시터 공통 적용이며 이후 사용자 변경이 우선한다. 외형 승인과 색감 승인은 별개다. 승인 체형/지느러미/꼬리/무늬/특징을 따르고 색감·명암·도트는 실제 저수지 원본20종을 기준으로 한다.
- 어종별 형태·핵심 특징·주/보조/강조색·명암·금지색·참조 역할/선정 이유를 명세한다. 물빠진 색/회색·누런 막/흐림/의도하지 않은 저채도 금지. 모든 종 금빛 통일/무조건 채도 상승 금지.
- 임시 컬러 시안이나 잘라낸 이미지를 생성의 초기/스타일/색 입력으로 넣지 않는다. 형태 입력은 색/배경을 분리해 실제 자료를 검토하며 흑백 변환만으로 해결됐다고 가정하지 않는다. 해당 종에 적합한 저수지 참조를 고르고 금빛 붕어 공통 강참조 금지. PixelLab 실제 요청 설정·전송 이미지를 확인한다.
- 승인 횟수 내 어종별1장 기본. 첫1종 생성→저수지 원본 비교 검수→통과 후 다음 종. 동시 유료요청 최대1개, 대량 예약/병렬/자동 재시도 금지. 원본 크기와 nearest 정수 확대에서 형태/색/명암/윤곽/특징/투명/잘림을 검수하고 기록한다. 파일 생성 성공과 품질 통과를 구분한다.
- 실패/부적합이면 후속 유료 호출 즉시 중단. 타임아웃 시 과금/작업ID/기존 결과부터 확인한다. 모델·seed·요청설정·참조경로/해시·결과해시·실제 차감·검수결과를 비밀키 없이 보존한다. 승인 없는 추가 유료 재생성 금지.
- 최초 거절20종은 임시 컬러 입력+공통 금빛 참조를 사용하고 문제 확인 후에도 계속해20회 차감한 실패 기록이다. 승인 참조/적용본/성공 사례로 재사용하지 않는다. 이후 최종 선택20종과 구분하며 현재 적용 상태는 HANDOFF/검증 문서에서 확인한다.
