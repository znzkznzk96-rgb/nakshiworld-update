# 레어 이상 물고기 등장 성능 조사

결론: 현재 연출을 유지하는 최적화 여지가 있다. 레어부터 매 프레임 실행되는 외곽 광채의 CPU 명령 생성이 가장 뚜렷한 추가 부하다. Android 실기기 프로파일이 없으므로 사용자가 겪은 모든 프레임 저하의 단일 원인 확정이나 개선 FPS 보장은 할 수 없다. 낚시 연출·밸런스·세이브 코드는 변경하지 않았다.

## 코드에서 확인한 경로
- main.gd의 hook_tap(): pre 단계 진입, encounter_at 및 visibility_flash 시작.
- pre 단계의 _draw_bite_shadow()는 등급 0/alpha 0.8로 호출한다. 따라서 광채 부하는 주로 fight 진입 이후다. 훅 성공 직후 글자만 나오는 순간의 끊김과 구분해야 한다.
- start_fight() 이후 _shadow_fish() → _draw_pixel_halo(): 레어 이상에서 3겹 × 8방향 × 몸체 12구간 × 삼각형 2개 = 576개의 추가 polygon 명령을 매 프레임 생성한다. 배열과 UV/색/좌표를 반복 할당·복사하며, text_layer의 ui_surface.paint에서 다시 순회한다. GPU 실제 draw call 수와 같은 의미는 아니다.
- 몸체만 24개 명령. 광채 및 작은 반짝임 포함 총 605/607/615/619개(레어/유니크/전설/신화). 같은 CPU 처리와 함께 반투명 실루엣을 24번 덧그리는 픽셀 처리량도 추가된다.
- 등장 글자: 글자별 폭 계산·그림자·광택. 전설 이상은 후광용 추가 글자도 _text()의 자동 그림자를 거쳐, 제목만 150개 text item을 만든다(레어 30개). 글꼴 첫 사용 비용은 추가 후보이나 실기기 GPU 글리프 업로드 비용은 측정하지 않았다.
- 등장 파티클은 15~30개, 총 90개 상한이 있다. 이 조사만으로 파티클을 주원인이라고 단정하지 않는다.
- 물고기 이미지 로드·실루엣 생성은 _ready()에 있으며, 훅 성공 시 매번 PNG를 다시 읽는 경로는 발견하지 못했다.

## 재현 측정
Godot 4.4.1 Linux headless, 각 조건 10회 워밍업+100회. 실제 _shadow_fish() 코드 호출, 합성 텍스처 사용. 물결 wake는 양쪽에서 제외. 격리된 Probe 서브클래스에서만 광채를 생략해 해당 경로 비용을 비교했다. 생략은 원인 분석용이며 적용할 최적화 방안이 아니다. 실제 화면 렌더/GPU/휴대폰 FPS는 포함하지 않는다.
결과 원본은 rare-cost.json. 첫 계측 스크립트는 draw 범위 밖 wake 호출 오류가 있어 폐기했고, wake를 양쪽 모두 제외한 정상 실행 결과만 사용했다.

## 모습 보존을 우선한 최적화 순서
1. 고정 UV·삼각형 인덱스·8방향 벡터를 재사용하고, 매 프레임 임시 배열 생성과 좌표 복사를 줄인다.
2. 같은 텍스처·색·렌더 순서의 삼각형들을 하나의 메시 단위로 묶는다. 광채 3겹, 8방향, 반경·색·투명도, 물고기 꼬리 변형은 유지한다. 576개 제출을 광채 24묶음으로 줄이는 것이 설계 목표이며, 아직 구현/검증한 성능 수치는 아니다.
3. 등장 문구의 글자 폭·배치를 캐시하고 필요한 글리프를 미리 준비한다. 현재 그림자와 후광 모양은 유지한다.
4. 같은 시드·시간·해상도의 전후 화면 차이를 비교하고 실기기에서 첫 등장/반복 등장 프레임 시간을 측정한다. GPU 덧그리기가 병목이면 명령 묶기만으로는 충분하지 않을 수 있다.

현재 단계는 조사 완료이며 낚시 연출 코드에는 최적화를 적용하지 않았다.
