> 활성브랜치 WORK_STATE.local_recovery.entry가 있으면 먼저 읽는다. 이전 절대경로가 새 환경에 존재한다고 가정하지 말고 명시된 실제 보존처를 사용한다.

# 새 채팅 이어하기

1. main의 START_HERE/AGENTS/PROJECT_INSTRUCTIONS와 WORK_STATE를 읽는다. work_branch가 가리키는 원격 브랜치의 최신 지침·WORK_STATE·HANDOFF를 우선 확인한다. GAME_BIBLE의 확정/미정 결정을 읽는다.
2. CHANGELOG 최신 항목, 실제 최신 Release 및 관련 Actions, 현재 workflow의 배포 조건을 확인한다. 상태 충돌은 최신 사용자 결정과 실제 원격 증거로 판단한다.
3. 같은 세션에서 읽은 자료는 SHA/관련 diff가 바뀐 경우에만 해당 부분을 갱신한다. 이력은 HANDOFF의 링크나 문제 추적에 필요할 때만 읽는다.
4. 게임 수정이 필요하면 최신 Release 전체소스ZIP을 검증해 복원하고 활성 브랜치 overlay/삭제 명세를 적용한다. 소스·도구·import 캐시는 기준이 맞으면 재사용한다. 문서 작업만이면 게임을 복원/빌드하지 않는다.
5. PixelLab 작업이면 활성 브랜치의 [PIXELLAB_CONNECTION](PIXELLAB_CONNECTION.md)을 먼저 읽고 검증된 기존 경로를 사용한다. 비공개 이어하기 안내를 통해 필요한 설정을 재사용하며, 사용자가 다시 설명/첨부/설치하게 만들지 않는다. 연결 확인만으로 유료 생성하지 않는다.
6. HANDOFF의 다음 작업을 진행한다. 확정사항을 재질문하지 않고, 사용자 준비 중 항목은 임의 설정하지 않는다. 실제 미정 결정이 작업을 막을 때만 관련 질문을 묶어 제시한다. 가능한 독립 작업은 계속한다.
7. 결과/현재 상태를 짧게 보고하고 PROJECT_INSTRUCTIONS의 검사·저장·배포 규칙을 따른다.

## 2026-11-05 — 읽기 전용 반복 시 재개 비용 제한
- 이 절차는 작업 유실·재조사 비용을 줄이는 운영 개선이다. ChatGPT의 읽기 전용 전환 자체를 고치거나 방지했다고 주장하지 않는다. 잔여 대화 한도/전환 시점은 확인 가능한 표시가 없으면 예측하지 않는다.
- main WORK_STATE는 활성 브랜치 탐색용이다. 실제 작업은 활성 브랜치 WORK_STATE의 handoff 경로를 정확히 따른다. 루트 HANDOFF만 보고 최신으로 판단하지 않는다. 오래된 첨부 START_HERE/전체 ZIP은 자동 복원하지 않는다.
- 새 채팅 첫 응답은 필요한 진입문서와 현재 handoff를 읽어 마지막 저장 SHA·완료/미완료·다음 한 단계부터 보고한다. 이후 작업에 필요한 파일만 읽는다. 전체 과거 이력/도구목록/API 응답을 통째로 출력하지 않는다.
- 긴 작업은 맵 연결 → 어종/장식 유영 → 번들 → 전체검증처럼 재개 가능한 단위로 나눈다. 각 의미 있는 단계에서 변경물·상태·검증 근거를 함께 work/*에 저장하고 원격 SHA/내용을 확인한다. 미완료 코드도 WIP/미검증으로 명시해 저장할 수 있으며 배포하지 않는다.
- 한도 직전까지 저장을 미루지 않는다. 한도 경고가 실제 표시되면 새 장시간 작업을 시작하지 않고 현재 결과를 먼저 저장한다. 이미 시작한 유료 요청은 결과/과금부터 확인하며 중복 실행하지 않는다.
- 새 채팅 안내에는 저장소·활성 브랜치·검증한 SHA·현재 handoff 경로·다음 행동만 넣는다. 전체 ZIP/이미지/이전 채팅의 재첨부를 기본 요구하지 않는다. 플랫폼이 시작 전 첨부를 준비하는 동작은 프롬프트로 통제할 수 있다고 약속하지 않는다.
- 사용자가 파일 준비 단계에서 새 채팅도 막힌다고 보고하면 동일 조건의 채팅을 반복 생성하도록 안내하지 않는다. 같은 대화 URL을 같은 계정의 모바일 웹에서 1회 비교하고, 필요하면 프로젝트 밖의 첨부 없는 새 Work 대화에 저장소와 짧은 재개문구만 넣어 1회 비교하는 진단을 제안한다. 원본 프로젝트/파일은 삭제하지 않는다. 이는 우회 진단이며 해결 보장이 아니다.
- 양쪽에서도 재현되면 대화 URL/발생시각과 시간대/앱 버전/정확한 문구/재현조건을 모아 지원팀에 세션 전환 사유·첨부 준비 실패·사용량 차감을 조사 요청한다. 내부 서버 로그 접근 없이 원인을 확정하지 않는다.
